# CWH 개발 방식과 협업 규칙

최종 정리: 2026-11-17

이 문서는 사용자와 협업자가 함께 코드를 작성할 때 따르는 작업 기준이다.
구현 상태는 이 문서나 과거 인수인계보다 **현재 코드와 실제 씬·프리팹 연결**을 우선한다.
사용자의 최신 요청이 이 문서와 다르면 해당 요청의 범위를 따른다.

## 1. 기본 협업 방식

사용자는 직접 코드를 작성하고 검토받으며 배우는 것을 기본으로 한다.

- “직접 만들어 줘”, “수정해 줘”, “구현해 봐”처럼 명확하게 요청한 범위는 직접 수정한다.
- “같이 만들자”, “어떻게 해결할까?”, “이런 방식이 좋겠다”는 먼저 읽기·분석·구현 안내로 진행한다.
- 읽고 조사하는 것은 진행할 수 있지만, 직접 수정 권한이 없는 요청을 임의로 파일 변경까지 확장하지 않는다.
- 특정 기능만 요청하면 그 범위를 지킨다. 한 번의 구현 허용을 이후 모든 작업의 상시 허용으로 해석하지 않는다.
- “됐어”, “작성했어”라고 하면 실제 작성한 코드와 저장된 참조를 읽고 검토한다. 작성했다고 가정하고 넘어가지 않는다.
- 파일을 수정하지 않았다는 말을 매번 반복하지 않는다. 실제로 수정했을 때 변경 내용을 알린다.
- 개념 문제나 퀴즈는 요청받았을 때만 진행한다.
- 스크립트를 작성할 때 네임 스페이스 기준은 Jetbrain에서 만든 Rider를 기준으로 네임 스페이스를 적는다.

## 2. 설명과 학습 안내

- 중학생도 따라갈 수 있도록 구체적인 예와 쉬운 표현을 사용한다.
- 낯선 문법은 이름과 동작을 함께 설명한다. 예: out, 이벤트 구독, 인터페이스, 보간.
- 왜 이 함수·계산식·자료구조를 사용하는지 설명한다.
- 개념을 이해했다는 이유로 복잡한 구현도 혼자 작성할 수 있다고 가정하지 않는다.
- 전체 기능의 완성 코드를 한꺼번에 주기보다 서로 연결된 작은 기능 단위로 안내한다.
- 한 줄마다 확인받지는 않는다. 준비·실행·정리처럼 함께 검토해야 하는 동작은 묶어서 진행한다.
- 새 스크립트가 필요하면 파일명, 생성 위치, 클래스부터 안내한다.
- 기존 파일 수정은 추가할 위치, 교체할 기존 구간, 그대로 둘 구간을 분명히 설명한다.
- 일부 코드만 제시한다면 선언되지 않은 변수나 필요한 선행 작업을 빠뜨리지 않는다.
- 코드 연결과 Inspector 연결을 구분한다. 자동 GetComponent 검색인지 직접 참조를 넣어야 하는지도 설명한다.

- 다른 멤버의 코드·에셋은 읽고 참조할 수 있으나 원본 변경은 하지 않는다.
- 다른 멤버의 시스템과 연결할 때는 CWH 내부의 어댑터, 연결 컴포넌트, CWH 전용 에셋 또는 씬 인스턴스 재정의를 활용한다.
- 기존 작업, 사용자가 변경한 Inspector 값, 다른 멤버의 미커밋 변경을 초기화하거나 덮어쓰지 않는다.
- 사용자가 정한 namespace와 현재 asmdef 경계를 확인하고 작업한다. 과거 안내의 경로나 namespace를 그대로 가정하지 않는다.
- Unity 에셋을 이동하거나 이름을 바꾸면 `.meta`도 함께 처리해 GUID와 참조를 유지한다.
- 코드를 작성·변경할 때 역할과 구현 이유를 설명하고, 필요한 이유 주석을 코드에 남긴다.

## 4. 설계 원칙: SOLID 우선

SOLID를 코드 구조의 우선 기준으로 삼되, 실제 필요 없이 인터페이스나 관리 클래스를 늘리지 않는다.

| 원칙 | 적용 기준 |
| --- | --- |
| SRP: 단일 책임 | 체력, 패턴 순서, 이동, 표시, 생성, 정리처럼 변경 이유가 다른 책임을 구분한다. |
| OCP: 개방·폐쇄 | 행동이나 표시를 추가할 때 공통 실행 흐름을 계속 고치지 않도록 필요한 확장 지점을 둔다. |
| LSP: 리스코프 치환 | 같은 계약을 구현한 객체는 호출자가 기대하는 준비·실행·취소·종료 규칙을 지킨다. |
| ISP: 인터페이스 분리 | 피해, 넉백, 공전 자세처럼 필요한 기능만 작은 계약으로 제공한다. |
| DIP: 의존성 역전 | 전투 로직이 특정 플레이어 구현이나 파티클 구현에 직접 묶이지 않도록 한다. |

구체 컴포넌트를 선택하고 조립하는 Factory나 연결 컴포넌트가 구체 타입을 아는 것은 자연스럽다.
구체 타입을 사용했다는 사실만으로 SOLID 위반이라고 단정하지 않는다.
검토할 때는 실제 동작 오류와 구조 개선 제안을 구분하고, 문제가 되는 변경 이유를 설명한다.

## 5. Unity 구현 기준

프로젝트는 Unity 6000.6.3f1을 사용해 왔으며 URP, Shader Graph, Cinemachine, Timeline을 사용한다.
정확한 현재 버전과 패키지는 프로젝트 설정을 확인한다.

- 코드의 초기값보다 씬·프리팹에 저장된 Inspector 값이 우선할 수 있다.
- 컴포넌트를 붙였다는 것과 실제 호출 경로가 연결됐다는 것을 구분한다.
- 콜라이더와 수신자의 위치, 같은 오브젝트 검색과 부모 검색의 차이, 레이어 마스크를 함께 확인한다.
- 체력 UI는 실제 페이즈 판단에 쓰는 체력과 같은 대상을 참조해야 한다.
- 같은 Transform을 공전·공격·회수 코드가 동시에 조작하지 않도록 상태와 제어권을 구분한다.
- 크기 연출은 저장한 기준 크기 × 배율로 계산한다. 현재 크기에 매 프레임 배율을 누적하지 않는다.
- 표시 범위와 실제 피해 범위를 구분하되 플레이어가 위험 범위를 읽을 수 있게 맞춘다.
- 공격 종료·취소·그로기·컷신·사망·비활성화에서도 예약, 이벤트 구독, 임시 객체와 전투 잠금이 남지 않도록 한다.
- 전투 잠금은 사유별 소유권을 유지한다. 컷신 하나가 끝났다고 다른 잠금까지 해제하지 않는다.
- UI나 이펙트를 부모에서 분리하면 추적 대상 파괴와 씬 종료 때의 수명 정리도 함께 구현한다.
- 기존에 꺼 두거나 주석 처리한 연출을 임의로 다시 켜지 않는다.
- 삭제 요청으로 제거했던 1페이즈 생성·연결 메뉴는 다시 만들지 않는다.

## 6. 보스 기능의 현재 합의

다음 항목은 임의로 의미를 확장하지 않도록 유지하는 기획 기준이다.

- 보스 체력이 최대의 60% 이하가 되면 2페이즈로 전환한다.
- 2페이즈 전환 때 살아 있는 검을 유지하며 부족한 만큼 6자루까지 한 번만 보충한다. 전투 중 파괴될 때마다 무한 보충하지 않는다.
- 검 투척은 한 자루씩 경고·준비·발사를 반복한다. 각 경고 시작에 위치를 정하고 해당 경고 중에는 추적하지 않는다.
- 투척 준비는 공전 바깥으로 이동하며 칼끝을 위로 세우는 방식이다. 발사 후 상승·공중 이동·수직 낙하하고 기존 회수 흐름을 사용한다.
- 근접은 타격마다 사용 가능한 다음 검을 선택한다. 한 자루만 남으면 재사용하며 나머지 공전 검은 계속 움직인다.
- 포효 직격은 직접 피해 없이 밀치기만 한다. 2페이즈 벽 충돌 추가 피해는 별도 규칙이다.
- 2페이즈의 점진적인 흑색 변화는 취소한 요구다. 기존 컷신의 외형 공개 방식을 기준으로 한다.
- 보스 피격과 공격 명중의 연출 재생 주체를 구분해 중복 카메라 흔들림을 피한다.

이 목록은 구현 완료를 보증하는 체크리스트가 아니다. 작업 시작 시 실제 파일과 연결을 다시 확인한다.

## 7. 검토와 검증

1. 관련 코드와 씬·프리팹 참조를 먼저 확인한다.
2. 문제의 원인과 수정 범위를 정한다.
3. 직접 구현 요청이면 필요한 변경과 연결을 완료한다. 학습 작업이면 작은 기능 묶음으로 작성 방법을 안내한다.
4. 변경과 관련된 컴파일 검사, 동작 테스트, 취소·복원·경계 상황 검증을 진행한다.
5. 결과를 변경 내용, 구현 이유, 검증 결과, 남은 제한으로 보고한다.

- 기존 Unity 세션을 강제로 종료하거나 주 프로젝트를 잠그지 않는다.
- 별도 검증 프로젝트와 재현 도구는 `C:\Users\WHChoi\Desktop\프로젝트 백업\Daramge\Validation`에서 관리한다. 요청·결과·스크린샷은 같은 Daramge 폴더의 `Verification`에 저장한다. CWH 안에 Validation~/Verification 폴더를 다시 만들지 않는다.
- 코드 검토, 컴파일, 자동 테스트, 실제 씬의 시각적 플레이 검증을 구분해서 보고한다.
- 과거 테스트 통과 수를 이후 변경 전체의 검증 결과처럼 말하지 않는다.
- 테스트는 실질적인 동작과 회귀 위험을 확인한다. 저위험 변경에 구현을 그대로 복제한 테스트를 무조건 늘리지 않는다.
- 현재 실제 씬에서 카메라, 입력 복구, 연출 가독성 등을 직접 확인하지 못했다면 그 한계를 명시한다.

## 8. 파일 정리 기준

- 삭제 전에 코드 사용처, Unity GUID 참조, 동적 로딩 가능성과 파일 출처를 확인한다.
- 확실한 생성 캐시·빌드 산출물부터 정리한다. 참조가 검색되지 않는다는 이유만으로 게임 에셋을 삭제하지 않는다.
- 오래된 일회성 도구와 검증 기록은 필요하면 압축 보관하고 보관본을 확인한 뒤 낱개 파일을 정리한다.
- 백업 압축파일은 `C:\Users\WHChoi\Desktop\프로젝트 백업\Daramge\Archives`에 보관한다. 게임 작업 폴더와 검증 프로젝트 안에 백업을 누적하지 않는다.
- 기존 백업을 외부 보관 위치로 옮길 때는 복사본의 SHA-256이 원본과 같은지 확인한 뒤 원본을 삭제한다. 검증 프로젝트·로그의 위치 변경과는 구분한다.
- 최신 검증 결과, 재현 방법, 학습 문서와 필요한 테스트 소스는 유지한다.
- 사용 중인 검증 프로젝트의 캐시는 지우지 않는다.
- 재귀 삭제·이동 전 실제 절대 경로가 CWH 작업 범위 안인지 확인한다.
- 주 프로젝트의 Library/Temp와 다른 멤버의 폴더는 CWH 정리 대상에 포함하지 않는다.
- 정리 결과와 보관 위치를 기록한다.
